# 설계

이 문서는 gate-kernel 이 **왜 이 형상인지**를 적는다. 사용법은 [`../README.md`](../README.md)와
플러그인 스킬에 있다.

## 1. 문제

LLM 이 만든 산출물을 검증하는 장치를 게이트라 부른다. 게이트는 두 레인으로 갈린다.

- **결정적** — 정규식, 구조 대조, 집합 연산. 같은 입력이면 같은 결과.
- **판정** — 문맥을 읽어야만 갈리는 것. LLM 이 본다.

문제는 레인이 두 개라는 게 아니라, **게이트마다 두 레인을 섞은 스크립트를 처음부터
다시 짠다**는 것이다. 다시 짜니 형상이 제각각이고, 제각각이니 캐시 키·재현·집계·리포트가
게이트마다 따로 논다. 그래서 게이트가 늘어날수록 게이트를 관리하는 비용이 게이트가
막아주는 결함의 비용을 넘는다.

프레임워크의 정의는 여기서 나온다: **가변부만 사용자가 쓰고, 불변부는 커널이 소유한다.**

| 커널이 소유 | 사용자가 쓴다 |
|---|---|
| diff base 해석, 파일 수집, 청킹 | `criterion` — 검사 가능한 한 문장 |
| 캐시 키·무효화, verdict 파일 계약 | `subject` — 무엇을 볼 것인가 |
| 판정 요청 물질화, 커버리지 검증 | `detect` / `scan` — 어떻게 좁힐 것인가 |
| 심각도 집계, 상태 판정, 리포트 | `judge` — 무엇을 물을 것인가 |
| 종료 코드 계약 | `skip` — 언제 이 규칙이 적용되지 않는가 |
| 면제 수명·만료, 스위트 선택 | `tags` — 이 게이트가 어느 축에 속하는가 |
| | `prove` — 실패를 어떻게 시연하는가 |

## 2. 왜 테스트 프레임워크를 그대로 못 베끼는가

`test(name, fn)` 의 `fn` 은 클로저다. 같은 프로세스에서 즉시 돌고, 싸고, 결정적이다.
게이트의 판정 레인은 셋 다 아니다 — **다른 컨텍스트에서 돌고, 비싸고, 비결정적이다.**

여기서 세 가지가 따라 나온다.

1. **`judge` 는 클로저가 아니라 데이터다.** 직렬화 가능해야 다른 컨텍스트(서브에이전트,
   다른 세션, 다른 호스트)로 넘어간다. `judge` 를 함수로 두면 프레임워크가 한 프로세스에
   갇힌다. 이 비대칭이 테스트 프레임워크와 게이트 프레임워크가 갈리는 지점이다.
2. **판정 결과는 캐시된다.** 비싸기 때문이다. 그리고 캐시하는 순간 `stale` 이
   일급 상태가 된다 — 테스트 프레임워크는 재실행이 싸서 이 상태가 필요 없다.
3. **결론이 아직 없음**을 표현할 코드가 필요하다. 그래서 종료 코드 `20`(JUDGE_REQUIRED)이
   통과(0)·실패(1)와 나란히 있다.

## 3. 불변식

등록 시점에 강제한다. 런타임이 아니라 저작 시점에 거부하는 것이 이 프레임워크의 핵심 가치다 —
잘못 만든 게이트는 조용히 통과시키는 게이트가 되고, 조용히 통과시키는 게이트는
없는 것만 못하다.

1. **결정적 좁히기 없는 게이트는 등록 거부.** `detect` 도 `scan` 도 없으면 판정자가
   레포 전체를 훑는다. 그러면 재게이트 루프가 수렴하지 않는다(§4).
2. **`judge` 에는 `because` 필수.** "왜 결정적으로 못 가르는가" 를 못 쓰면 그건
   결정적으로 되는 규칙이다.
3. **`judge` 는 `scan` 없이 붙일 수 없다.** `detect` 는 이미 결정된 결함만 낸다 —
   판정할 후보가 없다.
4. **위치 없는 결함은 거부.** `line: 0` 도 거부한다. 파일 전체를 가리키는 위치를
   허용하면 면제 한 줄이 통째 우회로가 된다.
5. **마스크에는 `reason` 필수.** 사유 없는 면제는 시간이 지나면 아무도 못 걷어낸다.
6. **마스크는 컬럼 정밀.** 줄 단위 면제는 같은 줄의 진짜 결함까지 삼킨다.
7. **`broken` 은 집계에서 제외되고 통과로 세지 않는다.** 판정 불가는 통과가 아니다.
8. **판정 커버리지 검증.** 후보 하나라도 답이 없으면 `broken`. 침묵을 통과로 접지 않는다.
9. **판정자는 슬라이스 밖을 못 본다.** 후보 밖 결함, 요청 밖 파일 읽기는 계약 위반이다.
10. **red 를 시연한 적 없는 게이트는 `unproven`.** 초록이 아니다.
11. **`skip` 은 사유 문자열을 돌려줘야 한다.** 사유 없는 건너뛰기는 조용한 초록과 같다.
12. **`mask[].until` 은 날짜여야 한다.** 파싱되지 않는 기한은 등록 거부. 기한이 지난
    면제는 효력을 잃고 결함이 되돌아온다.
13. **상한은 상한끼리 조인다.** `judge.cap` 이 `severityCap` 보다 느슨해도 낮은 쪽이
    이긴다 — 아니면 어드바이저리 게이트가 판정 레인으로만 차단 등급을 낸다.
14. **분류 태그가 없는 게이트는 모든 스위트에 든다.** 빠지는 게 아니라 드는 쪽이
    fail-closed 다(§9).

## 4. 결정적 좁히기 = 재게이트 루프의 고정점

게이트는 한 번 돌고 끝나지 않는다. 걸리면 고치고 다시 돌린다. 그래서 게이트의 실질
요건은 정확도가 아니라 **수렴**이다.

판정자가 스스로 대상을 넓힐 수 있으면 매 라운드 후보 집합이 달라지고, 고치면 다른 게
새로 나오는 상태가 무한히 이어진다(측정된 사례: 7 라운드까지 수렴하지 않음). 후보 집합을
결정적으로 만들면 그 집합이 **고정점**이 된다 — 고치면 줄고, 줄면 끝난다.

그래서 §3-1 과 §3-9 는 편의 규칙이 아니라 수렴 조건이다. 판정 에이전트의 도구를
`Read`/`Write` 로만 준 것도 같은 이유다 — `Grep`/`Glob`/`Bash` 가 없는 것은 실수가 아니라 설계다.

## 5. 비대칭 확인 (one-sided error)

- `→ red` 는 1표로 난다.
- `red → green` 은 확인 표 1장이 더 필요하다. 두 판정이 엇갈리면 red 를 유지한다.

LLM 판정의 오류는 대칭이 아니다. 거짓 red 는 사람이 보고 걷어내지만, 거짓 green 은
아무도 다시 보지 않는다. 그래서 비싼 쪽에만 표를 더 쓴다. 비용은 3배가 아니라
게이트 생애당 +1 이다 — green 전환은 게이트당 몇 번 없다.

## 6. red-first — 게이트의 오라클 문제

"이 게이트가 실제로 뭘 잡는가" 는 **테스트 오라클 문제**(Weyuker 1982; Barr et al.,
IEEE TSE 2015)의 한 형태다. 게이트 자신은 자기가 옳은지 모른다.

가장 값싼 오라클은 **실패 시연**이다. 위반 픽스처를 넣었을 때 red 가 나오는지 확인하면,
그 게이트가 최소한 아무것도 안 하는 게이트는 아니라는 게 증명된다. TDD 의 red-green
사이클과 같은 논리이고, `prove` 가 그 자리를 차지한다.

시연하지 못한 게이트는 `unproven` 이다. 등록은 되지만 초록으로 세지 않는다.
**결함 0 건과 검사 안 함은 관측적으로 구별되지 않기 때문이다.**

## 7. staleness 4축

캐시된 판정은 다음 넷 중 하나만 어긋나도 무효다.

| 축 | 무효화 사유 |
|---|---|
| `criterionRev` | 기준 문장이 바뀌었다 — 같은 결과라도 다른 질문에 답한 것이다 |
| `scanRev` | 좁히기(`detect`/`scan`/`skip`/`match`/`params`/`subject`)가 바뀌었다 |
| `maskRev` | 면제가 바뀌었다 |
| `subjectHash` | 대상 내용이 바뀌었다 |

면제가 축인 이유는 리포트가 하는 약속에 있다. "사유를 남겨라, 다음부터 안 묻는다" 는
방금 적은 마스크가 **다음 실행에** 먹는다는 뜻이다. 마스크를 캐시 키에서 빼면 그 약속은
대상이 바뀔 때까지 지켜지지 않고, 사용자는 같은 후보를 두 번 판정하게 된다.

여기에 시간이 하나 더 붙는다. 기한 만료는 아무것도 안 바뀌어도 일어나므로, 마스크가
살아 있을 때 저장된 판정은 만료 시점을 넘긴 순간 무효로 본다. 이 검사가 없으면
`until` 은 기한을 단 척하는 영구 면제가 된다.

에이전트의 자기보고("아까 확인했다")를 상태 판정에 쓰지 않는다. 해시와 시계가 판정한다.

## 8. 대상은 함수다

커널은 **무엇을 볼 수 있는지 열거하지 않는다.** `subject` 는 열거형이 아니라
`(env) => { label, files, data?, meta? }` 함수이고, 커널은 그 반환값에 해시를 붙여
슬라이스로 만든다. 새 대상을 위해 커널을 고칠 필요가 없다 — 게이트 파일에서 함수
하나를 쓰면 그게 대상이다.

```js
subject: (env) => ({ label: 'api-registry', files: 사내API(), meta: { cwd: env.cwd } })
```

열거하지 않는 이유는 `judge` 를 데이터로 둔 이유와 같다(§2). 커널이 종류를 열거하는
순간, 열거에 없는 대상은 "이 프레임워크로 못 만드는 게이트" 가 된다. 그 목록을 커널이
쥐면 게이트 저자는 커널에 PR 을 보내야 새 게이트를 쓴다.

커널이 소유하는 것은 종류가 아니라 **계약**이다. 대상이 무엇이든 해시·좁히기·캐시
무효화는 커널이 붙이므로, 사용자가 만든 대상도 staleness 계약을 우회하지 못한다.

`stdlib` 로 딸려 오는 `subject.*` 헬퍼는 자주 쓰는 형상을 미리 쓴 것일 뿐 특권이
없다. 코퍼스에서 역산한 목록이라 대부분 여기서 끝난다.

| 헬퍼 | 없으면 못 쓰는 게이트 |
|---|---|
| `tree` | 코퍼스 전수 검사 |
| `diff` (`addedLines` 포함) | 변경분만 — 기존 부채를 새 작업에 떠넘기지 않기 |
| `pair` | 고정 원본과의 드리프트, 크로스 레포 대조 |
| `command` (`baselineRef`) | 라이브 측정 델타(린트 증감 등) — 커밋된 베이스라인 파일은 갱신을 잊으면 조용히 거짓이 된다 |
| `external` | 이슈 트래커처럼 파일이 아닌 대상 |
| `rules` | 메타 게이트(룰 레지스트리 자신을 검사) |
| `all` | 판정식이 서로 다른 종류의 축을 **함께** 봐야 성립하는 게이트 |

`external` 은 provider 가 등록돼 있지 않으면 통과가 아니라 예외다(§3-7).

`all` 은 편의 합성이 아니다. "이 파일의 변경은 그것을 허락한 이슈에 합의가 모였을 때만
통과" 같은 판정식은 변경분 축과 이슈 축을 한 식에서 대조해야 한다 — 축을 쪼개면
각 게이트가 상대 축을 못 봐서 판정이 아예 성립하지 않는다. 반대로 쪼개도 각각
성립하면 쪼개는 쪽이 맞다. 큰 슬라이스는 비용과 오판을 같이 키운다.

## 9. 분류는 패싯이고, 소속과 선택은 분리한다

게이트가 수십 개가 되면 "이번엔 문서 게이트만" 이 필요해진다. 그래서 두 개가 있다.

- **소속** — 게이트가 자기 자신에 대해 선언하는 `tags: ['docs/terminology']`.
- **선택** — 레포가 선언하는 `suites: { docs: { include: ['docs/**'] } }`.

태그는 트리가 아니라 **패싯 분류**(Ranganathan)다. 한 게이트가 `['docs/api',
'code/contract']` 처럼 여러 축에 동시에 든다. 단일 트리로 만들면 그 게이트는 어느
한쪽에서 사라지고, 사라진 축에서는 통과처럼 보인다. 태그가 경로 모양인 것은 그것만으로
깊이를 표현하기 위해서다 — 커널은 축 목록을 갖고 있지 않다(§8 과 같은 이유).

둘을 한 곳에 합치지 않는 이유는 소유자가 다르기 때문이다. 중앙 카테고리 레지스트리를
두면 게이트를 하나 추가할 때마다 두 곳을 고쳐야 하고(single source of truth 위배),
`extends` 나 npm 으로 들어온 남의 게이트는 자기 소속을 들고 올 방법이 없어진다.

태그가 없는 게이트는 **모든 스위트에 든다.** 빠뜨리는 쪽이 아니라 드는 쪽을 고른 것은,
분류 누락이 커버리지 누락으로 번지면 그 게이트가 "돌지 않는데 통과" 로 보이기
때문이다. 대신 실행마다 경고가 찍힌다.

## 10. 조건부 실행 — 미적용은 통과가 아니다

"이번 변경에 `.sql` 이 없으면 마이그레이션 게이트는 안 돌린다" 는 게이트가 늘 걸리는
것을 막는 정당한 요구다. 다만 안 돈 게이트를 초록으로 세면 §6 이 막으려던 것과 같은
거짓말이 된다 — 결함 0 건과 검사 안 함이 다시 구별되지 않는다.

그래서 `skip` 은 불리언이 아니라 **사유**를 돌려준다. 커널은 "대상 파일이 원래 없다"
와 "대상 파일이 전부 지워졌다" 를 구별할 수 없고, 그 구별은 게이트만 할 수 있다.
사유가 비면 `broken` 이다.

건너뛴 게이트는 `skipped` 상태로 집계에서 빠지고, 리포트에서 통과와 **다른 문단**에
"이번엔 안 돌았다" 로 나온다. `skip` 판정은 캐시보다 앞에 있다 — 뒤에 두면 캐시된
green 이 안 도는 게이트를 통과로 재생한다.

## 11. 면제의 수명

면제에는 두 종류가 있고 소유자가 다르다.

- **게이트가 들고 오는 것**(`rule()` 의 `mask`) — 그 규칙에 본질적인 예외.
- **레포가 결정하는 것**(`gate.masks.json`) — 이 레포에서만 통하는 예외.

레포 면제를 캐시 디렉토리(`.gate`)가 아니라 커밋되는 파일에 두는 이유가 핵심이다.
캐시는 보통 gitignore 이고, 거기 쌓인 면제는 diff 에 안 나타나 아무도 리뷰하지 않는다.
**리뷰되지 않는 면제는 게이트를 끈 것과 같다.** 파일로 두면 npm 으로 받은 게이트도
면제할 수 있다 — 남의 패키지 소스는 고칠 수 없기 때문이다.

`until` 은 없어도 된다. 게이트가 진짜로 틀렸을 때의 정정은 부채가 아니라서 기한을
붙이면 오히려 거짓이다. 다만 **적었으면 지킨다** — 날짜가 아닌 문자열은 등록에서
거부되고(§3-12), 기한이 지나면 면제는 없는 것이 되어 결함이 그대로 돌아온다. 돌아온
결함 옆에는 어떤 면제가 언제 만료됐는지가 같이 나온다. 조용히 되살리면 사용자는
게이트가 고장 난 줄 안다.

면제는 `gate mask <rule> <code>` 로만 적는다. 게이트가 실제로 낸 code 가 아니면
거부되고, 위치는 그 게이트가 낸 것에서 그대로 가져온다 — 손으로 파일 전체를 가리키는
면제를 쓸 수 없게 하기 위해서다(§3-4).

## 12. Goodhart 대책

게이트는 측정이고, 측정은 목표가 되는 순간 좋은 측정이길 그친다(Goodhart 1975;
Strathern 1997). 이 프레임워크가 거는 방벽은 셋이다.

- 면제는 **컬럼 정밀 + 사유 필수**(§3-5, §3-6)에 커밋되는 파일이다(§11) — 우회가 싸지 않고,
  싸게 하려면 리뷰를 통과해야 한다.
- 실패 시연 없이는 초록이 아니다(§6) — "게이트를 통과했다" 가 "게이트가 아무것도 안 한다"와
  같아지지 않는다.
- 늘 걸리는 게이트는 곧 무시된다. 그래서 `subject`/`match` 로 대상이 없으면 아무것도
  요구하지 않게 좁히는 것을 저작 규칙으로 못박는다.

## 13. 반증 조건

이 설계가 틀렸다면 다음 중 하나로 드러난다. 미리 적어 두는 이유는, 나중에 편한 쪽으로
기준을 옮기지 않기 위해서다.

1. 결정적 좁히기를 강제해도 재게이트 루프가 수렴하지 않는다.
2. red-first 를 강제한 게이트가 강제하지 않은 게이트보다 결함을 덜 잡는다.
3. `stale` 4축이 에이전트 자기보고보다 재판정 필요를 못 맞춘다.
4. `scan` 없는 게이트를 거부하는 것이 실무에서 표현 불가능한 규칙을 다수 만든다.
5. `skip` 의 사유 강제가 형식만 남는다 — 사유는 적히는데 게이트는 사실상 꺼져 있다.
6. 만료된 면제가 되돌아온 결함을 사람이 고치지 않고 기한만 미루는 데 쓰인다.

되돌리는 근거는 실증이다. 몇 번 해보고 안 된다는 건 근거가 아니다.
